# Backend Guide

This file is the source of truth for backend agent instructions.

## Goal

The backend is a TypeScript + Express template designed to expose a clean HTTP API with:

- PostgreSQL
- Swagger
- Prometheus metrics
- health checks
- Zod validation
- SQL migrations and seeds
- optional notifications, mailer, and storage services (local or S3)
- optional background job scheduler
- pgtyped typed queries

The target is a backend base that is simple, readable, and directly deployable.

## Strict Rules

### Rule 0: Never create `.types.ts` manually

Files matching `src/db/query/**/*.types.ts` are generated by `pgtyped` only.

Allowed flow:

- write the `.sql` file in `src/db/query/<entity>/`
- start the database from `docker/` with `docker compose --env-file .env up -d db`
- run migrations from `backend/` with `npm run db:migrate`
- generate types from `backend/` with `npm run pgtyped`

Coding agents must run this flow themselves: the backend does not compile until the generated `*.types.ts` files exist, so generating them is part of the task — never a manual follow-up left to the user. Commit each generated `*.types.ts` alongside its `.sql` file and the migration that backs it.

Forbidden:

- manually creating `*.types.ts`
- manually editing `*.types.ts`
- copying or adapting pgtyped internal structures by hand

Reason:

- pgtyped internal representations rely on exact character offsets computed from the SQL source
- hand-written or partially edited generated files can create silent runtime failures
- only `npm run pgtyped` should produce these generated artifacts reliably

### Rule 1: No raw SQL in services or controllers

- all SQL belongs in `src/db/query/<entity>/`
- services consume generated pgtyped code
- do not use `pool.query()` in services for business queries
- do not use `client.query()` in controllers

### Rule 2: Strict env validation

The app must fail at startup when required env vars are missing.

Always required:

- `DATABASE_HOST`
- `DATABASE`
- `DATABASE_USERNAME`
- `DATABASE_PASSWORD`

Required when JWT is enabled:

- `JWT_KEY`

Required when `STORAGE_DRIVER=s3`:

- `STORAGE_S3_ENDPOINT`
- `STORAGE_S3_BUCKET`
- `STORAGE_S3_ACCESS_KEY`
- `STORAGE_S3_SECRET_KEY`

See [docs/EnvVariables.md](docs/EnvVariables.md).

### Rule 3: Use pgtyped for DB type safety

- database queries must be typed through pgtyped
- do not cast DB results to `any`

### Rule 4: No magic strings or numbers

- use typed constants or centralized union types
- centralize HTTP statuses, error messages, strategy names, and driver names
- do not scatter `"api-key"`, `401`, `500`, and similar values through business logic

## Getting Started

1. Copy `.env.example` to `.env` and configure it.
2. Run `npm run db:migrate`.
3. Start local development with `npm run dev:api`.
4. For a new domain/resource, follow the resource convention below.

## Authentication

Authentication is handled through `src/middleware/auth/authenticate.ts`.

Supported strategies:

- `jwt`
- `api-key`

Active strategies are defined by `AUTH_STRATEGIES`.

### JWT

Implementation:

- `src/middleware/auth/strategies/jwt.ts`

Current payload contract:

```ts
export interface AuthTokenPayload {
  data: string;
  iat?: number;
  exp?: number;
}
```

`data` represents the user email.

### API key

Implementation:

- `src/middleware/auth/strategies/apiKey.ts`

Supported sources:

- header configured by `API_KEY_HEADER`
- `Authorization: ApiKey <key>`

The auth middleware may enrich `req` with:

- `req.user`
- `req.user_id`
- `req.email`
- `req.requestId`


- define payload contracts in `src/controllers/<resource>/types.ts`
- reserve `src/types/*` for shared cross-domain types
- define schemas in `src/schemas/*`

## Metrics And Observability

### Request ID

Middleware:

- `src/middleware/observability/requestContext.ts`

### HTTP logging

Middleware:

- `src/middleware/observability/requestLogger.ts`

It logs method, path, status code, duration, and request ID.

### Prometheus metrics

Helper:

- `src/helpers/metrics.ts`

It exposes default Node.js metrics, an HTTP counter, and an HTTP histogram.

Endpoint:

- `GET /metrics`

### Rate limiting

Middleware:

- `src/middleware/security/rateLimit.ts`

Provide separate limits for:

- API
- auth
- Swagger docs
- metrics

Keep auth limits stricter than general API limits, and keep `health/live` and `health/ready` outside the global rate limit.

## Background Jobs

Optional cron-based jobs, gated by `FEATURE_JOBS`.

Entry point:

- `src/jobs/scheduler.ts`

Rules:

- centralize job names and cron expressions in `src/jobs/jobConstants.ts`
- one job per folder under `src/jobs/<job>/`, following `src/jobs/example/`
- a job is an async function returning a summary object; the scheduler logs it
- register new jobs in `startScheduler()`; the scheduler is wired into the lifecycle and stopped on shutdown
- never throw to the scheduler — `runJob` already isolates and logs failures

## Convention For Adding A Resource

Creation pattern:

1. `src/routes/<resource>.ts`: HTTP routes, validation, auth, no business logic
2. `src/schemas/<resource>.ts`: Zod schemas per operation
3. `src/controllers/<resource>/types.ts`: request and response contracts
4. `src/controllers/<resource>/index.ts`: domain assembler, instantiates service and injects it into CRUD handlers
5. `src/controllers/<resource>/<resource>CRUD.ts`: HTTP handlers, service injected through constructor, never instantiate the service inside the handler file
6. `src/services/<resource>/<resource>Service.ts`: business logic, one method per operation, no union returns such as `T | T[]`
7. `src/db/query/<resource>/`: pgtyped queries only

### Controller structure rules

- `index.ts` is the assembler of the domain
- it creates the service and injects it into CRUD classes
- CRUD classes receive the service in their constructor
- separate files by responsibility when needed, then aggregate from `index.ts`

Example pattern:

```ts
const service = new MyService(db);
const crud = new MyCRUD(service);
this.getById = crud.getById.bind(crud);
```

Constructor injection pattern:

```ts
constructor(private myService: MyService) {}
```

### Service structure rules

- one method per operation such as `getById(id)` and `list()`
- strictly typed returns
- no direct SQL outside `src/db/query/<resource>/`

### Route structure rules

- one route definition and one validation schema per HTTP operation
- `GET /<resource>` for list
- `GET /<resource>/:id` for get-by-id
- `POST`, `PUT`, `DELETE` with dedicated body schemas

### Full example structure

```text
src/
  routes/product.ts
  schemas/product.ts
  controllers/product/
    types.ts
    index.ts
    productCRUD.ts
  services/product/
    productService.ts
  db/query/product/
    getProductById.sql
    listProducts.sql
```

## Docker

The Docker stack is described in `docker/docker-compose.yml` at repo root.

Typical commands from `docker/`:

```bash
docker compose up -d db
docker compose run --rm migrate
docker compose up -d website
```

Seeds load dev-only demo data — run them deliberately with `npm run db:seed` (or the one-shot `seed` service), never as part of a production deploy.

Important services:

- `db`: PostgreSQL with health check
- `migrate`: one-shot migration job
- `seed`: one-shot seed job
- `website`: HTTP application

Container naming convention:

- `website`: `${ENVIRONMENT}-${APP_NAME}`
- `migrate`: `${ENVIRONMENT}-${APP_NAME}-migrate`
- `seed`: `${ENVIRONMENT}-${APP_NAME}-seed`
- `db`: `${ENVIRONMENT}-${POSTGRES_DB}-db`

## Lifecycle And Shutdown

Lifecycle is centralized in `src/helpers/lifecycle.ts`.

The API boot registers shutdown handlers for:

- HTTP server
- job scheduler
- PostgreSQL pool
- storage
- notifications
- mailer

Goals:

- clean shutdown on `SIGINT` and `SIGTERM`
- release open connections and resources

For tests or multiple boots in the same process, use `resetLifecycleState()`.

## Working Rules

- keep `src/index.ts` reserved for bootstrap
- keep `src/apps/*` for entry points
- keep `src/routes/*` free of heavy business logic
- keep `src/controllers/*` centered on HTTP concerns
- use `services/` for reusable business logic
- use `types/` for stable API contracts
- use `logger` instead of `console.log`
- use `AppError` and derived errors for expected failures
- add Swagger annotations for new public routes
- use `authenticate(pool)` when a route must be protected
- add any new global convention to this file
